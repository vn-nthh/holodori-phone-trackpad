# Doritrack v0.6.0-alpha1 — experimental protocol V6

This prerelease replaces the authenticated V5 transport with protocol V6. It
keeps every V5 guarantee and spends fewer datagrams and round trips on the
same lossless input. It is built from the `protocol-v6` branch, on top of
v0.5.2.

## Update both devices together

V6 is not wire-compatible with V5. A v0.6 PC host will not talk to a v0.5.x
phone app, and the reverse. Install the Windows and Android apps from this
same release.

Pairing identities are unchanged: a phone already paired with this PC under
v0.5.x stays paired, and the Android app updates earlier v0.5.x builds in
place, keeping settings and pairing. V4 remains available only through the
explicit legacy USB selection.

## Changes

- **Faster session start.** The PC's session parameters now ride inside the
  encrypted pairing-handshake reply, so the phone starts sending input the
  moment the handshake completes. The separate V5 hello step and its repair
  loop are gone. The PC checks the route and the tether policy before
  replying, so a refused path never starts a session on the phone.
- **Fewer packets for queued input.** Frames that are already waiting to be
  sent share one encrypted datagram (up to 16). Every frame keeps its own
  sequence, sample time, and complete contact snapshot, and the PC applies
  each one in order. A send is never delayed to fill a datagram.
- **Selective ACKs.** The PC reports which frames it already holds behind a
  gap, and the phone stops repairing them.
- **One ACK per progress step and single-copy heartbeats.** The PC no longer
  sends every ACK twice, and the 8 ms hold heartbeat is sent once. A lost ACK
  or heartbeat is repaired after 2 ms like any frame. New touch samples still
  get an immediate redundant copy.

## Validation and experimental limits

Local optimized Windows loopback, with final OS acceptance simulated:

- healthy delivery and one lost or corrupt copy: worst 0.067 ms
  (0.42 ms with diagnostics on);
- both immediate copies lost: p99 3.03 ms, worst 3.42 ms, repaired by the
  2 ms replay.

Every case is below the 8.333 ms target. These numbers do not establish
physical phone-to-game latency. No real phone/cable/PC or phone/router/PC soak
has been run on this build yet, so please report any missed or stuck input,
and whether the connection starts and recovers reliably over USB and Wi-Fi.
